_Evidence: file:line in this repo, numbers measured in this session, and screenshots in `docs/audit-2026-11/`.
The measuring scripts are in `docs/audit-2026-11/scripts/` (run from the repo root, e.g.

## The 5 things that matter most (plain English)

1. **Your access token has never been changed since the repo was public.** The fingerprint of the live token
   matches the one committed in `db/setup01.sql` while the repo was public (still in git history, commits 72dc747
   and 7588b19). That committed value is a fast, unsalted hash, so a short or word-like token can be guessed
   offline. Anyone who has it can read and change everything, straight against Supabase, without going through
   the app. Changing the token is the single most valuable fix. _(No sign of misuse: all 3,125 database calls in the
   last 24 h came from the app's own server and all succeeded.)_
2. **Connecting Google Calendar sends your token to Google.** The sign-in step puts the token, only base64-encoded,
   in the `state` parameter of Google's sign-in address and in your browser history (`api/gcal.js:35`,
   `public/js/saver.js:262`). Small fix.
3. **The Work board makes the iPad flicker every 15 seconds.** It resets its scroll positions on every background
   refresh even when nothing changed (`public/js/board.js:302-308`) — the exact iOS 9 problem already fixed in
   My projects. Small fix.
4. **The app asks the server for everything 240 times an hour.** On any main screen it downloads the full task list
   (~80 KB, half of it tasks you finished this week, 42 % empty fields) every 15 s, plus an Apple Calendar sync every
   2 minutes. The iPad copes (each tick is cheap), but it is 276 server calls an hour for a list that changes a few
   times a day. A "has anything changed?" check would cut this by ~90 %.
5. **The app is starting to sprawl.** Three different "Projects" (Work board, My projects, and a default category
   called Projects), 9 rail items plus a "Workouts" placeholder, chips that are 24–31 px tall instead of 44 px, and
   the same code written three to five times (drag, loading, statuses). Nothing is broken, but each new feature costs
   more and looks a little less consistent.

Recommended first (details at the end): **token rotation**, **Google sign-in fix**, **board flicker + late-token
loading fix**, then **polling diet**.

## 1. Performance (iPad 2 profile)

### 1.1 What the iPad downloads on first load
Measured from the repo (`wc -c`, `gzip -9`). Vercel serves these compressed; the live headers could not be read
from this session (the workspace cannot reach the site and Chrome was not connected).

| File | Raw | Gzipped |
|---|---:|---:|
| `index.html` | 13.8 KB | 4.4 KB |
| `app.css` + `work.css` | 37.8 KB | 8.9 KB |
| `core.js` | 105.3 KB | 27.6 KB |
| `pprojects.js` | 91.4 KB | 25.0 KB |
| `budget.js` | 40.5 KB | 12.0 KB |
| `board.js` | 34.5 KB | 10.4 KB |
| `insights.js`, `projects.js`, `saver.js`, `workcal.js`, `calendar.js` | 67.9 KB | 21.5 KB |
| **All JS (9 files)** | **339.6 KB** | **96.6 KB** |
| **Total HTML + CSS + JS** | **391 KB** | **110 KB** |

- **Requests:** 1 HTML + 2 CSS + 9 JS + up to 3 icons = 15 static, plus **9 API calls at startup** (measured: `/api/todos`
  ×2, `/api/projects` ×2, glance, settings, pprojects, cal, gcal). `/api/projects` is fetched twice by two modules
  (`board.js:585` and `projects.js:12`), again twice on every return to the app (`board.js:573`, `projects.js:13`).
- **Minify (measured with terser `--ecma 5`, output passes `tests/es5.js`):** JS 339.6 → 226.0 KB raw (−33 %),
  96.6 → 77.6 KB gzipped (−20 %). The raw saving matters more than the gzip one on the iPad 2: Safari 9 has to parse
  every byte. About 13.8 KB of `pprojects.js` is CSS held in a JS string (`pprojects.js:31-139`), which a minifier
  cannot shrink.
- **Cache headers (from config, not measured live):** `vercel.json` only sets `no-cache` for HTML. JS, CSS and icons
  therefore get Vercel's default, which makes the browser re-check every file on each load. Because every script and
  stylesheet URL carries `?v=1049` and `build.py` bumps it on every change, a long `immutable` cache for `/js/*`,
  `/app.css`, `/work.css` and the icons would be safe. API responses send `no-store` (all `api/*.js`); the two image
  routes send `private, max-age=31536000, immutable` (`api/saver.js:33`, `api/pprojects.js:271`), keyed by `&v=`.
  Note: the app reloads itself whenever the theme flips at night start/end (`core.js:1500-1507`), so the iPad does a
  full load at least twice a day.

### 1.2 The task list payload (`GET /api/todos`)
Measured read-only on the live database:
- `todos` holds 213 rows; `todo_list` returns **109** (55 open + 54 done in the last 7 days), 37 fields each.
- Size: 90.7 KB as Postgres prints it; the API re-sends it compactly, **≈ 82 KB (≈ 760 bytes per task)**.
  At twice today's tasks: **≈ 165 KB**.
- **42 % of it is empty fields:** stripping nulls takes it to 52.5 KB; also dropping fields the page never uses
  (`updated_at`, `cal_etag`, `cal_sig`, `cal_uid`, `successor_id`) gives 46.4 KB.
- **Half the rows are finished tasks** (54 of 109), sent every 15 s for the "Done this week" list and counts.
- Gzipped size could not be measured live; a mock with realistic, varied titles gzips 75 KB → 7.7 KB (2× → 14.8 KB).
  So bandwidth is modest if Vercel compresses; the costs are the number of calls and the parse/render work.
- `todo_list` returns `to_jsonb(t)`, i.e. every column, including calendar sync internals (`db/setup14.sql`).

### 1.3 What runs while the app sits idle
Measured with Playwright's fake clock, one simulated hour, mocked API (`scripts/audit_calls.py`):

| Screen | API calls per hour | What |
|---|---:|---|
| Personal / Work / My projects (Apple Calendar off) | **246** | 240 × `GET /api/todos`, 6 × glance |
| Same, Apple Calendar connected | **276** | + 30 × `POST /api/cal?sync=1` (every 2 min, although the comment says 5: `core.js:941-942`) |
| Screensaver, plugged in | 25 | 10 × todos (every 10 min), 12 × Google events, image fetches (cached) |
| Screensaver, battery | 16 | rests after 10 min, events stop |

Real traffic agrees: in the last 24 h Supabase served **1,220 `todo_list`** and **897 `cfg_get`** calls (calendar and
glance config), ~3,100 todo-app RPCs in total, all from the app's server (`node`), all HTTP 200.

Timers behind this: core `load()` + `App.render()` every 15 s (`core.js:1673`, every 10 min when idle), clock every
10 s (`:1674`), glance every 10 min (`:1675`), saver check every 10 s (`saver.js:121`), vault idle check every 15 s
(`pprojects.js:888`), plus `load()` on `focus`, `pageshow`, `visibilitychange` and `webkitvisibilitychange`
(`core.js:1669-1672`) and one more `visibilitychange` reload in each of board, pprojects, projects and workcal.
Returning to the app fires **5 API calls** at once (measured).

**How much DOM each 15 s tick rewrites** (spying on `innerHTML`, `value` and `scrollTop` writes during a background
reload with unchanged data, `scripts/audit_perf.py`):

| View | innerHTML writes | value writes | scrollTop writes | string-building cost per tick (6× CPU) |
|---|---:|---:|---:|---:|
| Personal | 0 | 0 | 0 | 3.9 ms |
| Work | 0 | 0 | 0 | 7.8 ms |
| Tomorrow | 0 | 0 | 0 | 0.1 ms |
| **Work board** | 0 | 0 | **3** (+ `scrollLeft`) | 2.7 ms |
| My projects board | 0 | 0 | 0 | 1.5 ms |
| **My projects, project page** | **4** (`#viewTitle`) | 0 | 0 | 2.9 ms |
| Budget, Insights | 0 | 0 | 0 | ≤ 1.2 ms |

So `App.setHTML`'s "only write when changed" works almost everywhere. The two exceptions:
- **Work board** restores `scrollLeft`/`scrollTop` after every paint even when `setHTML` returned false
  (`board.js:302-308`). On iOS 9 these writes repaint touch-scroll areas (the flicker described in CLAUDE.md).
- **Project page title**: core writes "My projects" (`core.js:388`), then pprojects writes "My projects + name"
  (`pprojects.js:734`), twice per tick — the title is rewritten 4 times every 15 s.

A real change (e.g. ticking a task) rebuilds the three task columns: **42 ms at 109 tasks, 54 ms at 218** (6× CPU).
Parsing the payload: ~1.2–1.6 ms. `planNo()` loops over all tasks and is called inside sort comparators and twice per
row (`core.js:139-154`, `:320`), so the cost grows faster than the list; fine today, worth fixing before it doubles.

### 1.4 First load, throttled
Chromium with CPU throttled 6×, mocked API with zero network delay, 1024×768:
- Tasks visible in **0.75–0.89 s** (first cold run 1.5 s); DOMContentLoaded 0.6–0.7 s; script 0.15–0.24 s;
  layout 0.16–0.18 s; 895 DOM nodes (1,187 at 2× tasks).

**How far to trust this:** treat these as *relative* numbers (before vs after a fix). A modern x86 core at 6× is
roughly a 2016–18 phone; an iPad 2 (A5, 512 MB, Safari 9's older JavaScript engine) is plausibly another 3–5× slower,
and the mock adds no network or Vercel cold-start time. Real load time, scroll feel and cursor behaviour need the
device checklist at the end.

### 1.5 Database
- `todo_list`: 3.8 ms (sequential scan of 213 rows, sort in memory). `pproj_list`: 0.7 ms, all sub-queries use
  indexes. The database is not a bottleneck; Vercel function start-up and the network dominate.
- Performance advisor: one finding for this app, `todos.successor_id` foreign key without an index (harmless at 213
  rows). Table sizes: todos 144 KB, `saver_images` 11 MB (26 images, ~430 KB each as stored).

## 2. Code quality

**Structure.** `core.js` (1,766 lines, 240 functions) holds state, dates, network, sorting, rendering, the editor,
Tomorrow, preview, review, settings and the click dispatcher. It exposes 48 members on `window.App`; modules add 5
more, including a test hook in production (`App.ppVaultAge`, `pprojects.js:889`). `pprojects.js` (1,208 lines,
168 functions) holds the board, project page, costs, icons, Vercel picker, vault UI and its own drag code.

**Duplication (measured):**
- **Load-with-retry, 5 copies:** `board.js:15`, `pprojects.js:146`, `projects.js:9`, `workcal.js:10`,
  `calendar.js:12`. Each gives up after 8 tries × 1.5 s. **Bug (reproduced):** if the token is typed in more than ~12 s
  after the page opens (new device, or after "token not accepted"), My projects, Work project priorities, the Google
  work-calendar prompt and calendar status never load until the app is backgrounded. My projects then shows
  "Loading…" indefinitely and shelved tasks count as normal (`scripts/audit_gate.py`).
- **Touch/mouse drag, 3 implementations:** `core.js:1139` (Tomorrow/preview/session), `board.js:313-363`,
  `pprojects.js:1139-1190`.
- **Statuses in four places:** DB check + `pproj_save`, `api/pprojects.js:42`, `core.js:166` (`PP_SHELF`),
  `pprojects.js:11-15` (`STAT/LABEL/SHELF/NOTLIVE`). Already noted in CLAUDE.md.
- **CSS outside the CSS files:** `pprojects.js:31-139` (13.8 KB), `board.js:10` (duplicates `.pau` from
  `work.css:137`), `shell.html:178-182` (full-screen button). Colours there are hard-coded hex (board 7, work.css 21)
  and do not follow the night theme tokens (`app.css:12`).
- **Sorting/rows:** core has one row renderer (`itemHTML`) used everywhere via `App.listHTML` — good. Tomorrow rows,
  preview rows, board rows and project cards each build their own chips.

**Fragile spots:**
- **12 document-level click listeners** (one per module, two in pprojects/projects/workcal) each walk up from every
  tap; core's is a ~90-branch `if/else` chain (`core.js:1529-1631`). Works, but order-dependent: a module must stop at
  `data-act` (CLAUDE.md pitfall).
- **Form-class clash:** `board.js:545` takes any form whose class *contains* `bdadd` (substring match).
- **`meta` replaced whole on save:** each form must copy keys it does not edit (`pprojects.js:801`, `:1005`). The
  server protects `icon`, but the next new meta key will repeat the `reason` bug unless the API merges.
- **Hidden-element toggles:** rail items start `display:none` and appear when a module registers (`core.js:1753`),
  so a module that fails to load silently removes its tab.
- **Theme flip reloads the page** (`core.js:1500-1507`) — deliberate for iOS 9, but it discards unsaved typing if it
  fires (it waits for open sheets, not for the add box).

**Error, empty and loading states:**
- Core: failed reload shows "offline, retrying" in the stats line (`core.js:98`, `:446`) — good.
- Work board: only handles HTTP 200, no failure flag, so a failed load shows "Loading…" forever (`board.js:15-17`, `:277`).
- My projects: has a failure message (`pprojects.js:433`) but not for the late-token case above.
- Project with no tasks: friendly empty texts ("Nothing from this project in your Personal list", screenshot
  `ipad-land-project-page.jpg`).
- First load with no token: gate appears; modules may then never load (above).
- Vault locked/expired: handled and tested (172 checks pass, see 4.4).

**Accessibility basics:** `lang="en-GB"`, 38 `aria-label`s, real `<button>`s for most actions. Task bodies are
clickable `<div>`s (not keyboard-reachable; fine for touch). Muted text `#8a8174` on `#f4eee1` is **3.3:1** (night
3.4:1), below the 4.5:1 guideline for small text.

## 4. Security and data hygiene

### 4.1 Secrets in the repo and client
- **Old token hash in history:** HEAD has the placeholder (`db/setup01.sql:118`), but commits **72dc747** and
  **7588b19** contain a real hash, and its fingerprint matches the live `token_sha256`. The token has not been rotated.
  The repo is now private (checked).
- Test files contain fake secrets only (`tests/`). No keys or tokens found in other files or history (regex scan for
  JWTs, `sk_`, `ghp_`, Vercel tokens, 64-hex values).
- Client code holds no keys; the token lives in `localStorage` (`core.js:1761`).

### 4.2 Token handling
- **Google sign-in leaks the token:** `/api/gcal?action=start&t=<token>` is a full page navigation (browser history),
  and `makeState()` puts `{t: token}` base64-encoded (signed, not encrypted) into Google's `state` parameter
  (`api/gcal.js:35`, `:246-255`).
- **`?t=` accepted on every endpoint**, including writes (e.g. `api/todos.js:245`, `api/pause.js:23`). Needed only
  for calendar feeds (`/api/ics`), the two image routes and the Google start link; in URLs it can land in Vercel's
  request logs.
- **`#t=` set-up links stay in the address bar:** the token is read from the hash but the hash is never cleared
  (`core.js:1759-1760`; saver.js already clears `#gcal` with `replaceState`).
- **Direct Supabase path:** every todo RPC is executable by the `anon` role (security advisor: 54 warnings; grants
  confirmed, e.g. `todo_list`, `pvault_attempt`), because the API itself uses the anon key. With the token, anyone can
  call them directly at Supabase, bypassing Vercel — including `pvault_attempt(ok=true)`, which resets the vault's
  5-try lockout. Last 24 h: no such traffic (every RPC came from `node`, all 200).
- Wrong tokens cost 0.5 s each (`todo_check`) but there is no lockout.

### 4.3 Other server-side findings
- **Calendar credentials key:** the Apple app password and Google refresh token are encrypted with a key derived from
  `CALDAV_KEY`, which is not set, so it falls back to `SUPABASE_KEY` (`api/cal.js:19`, `api/gcal.js:20`). That key is
  the publishable anon key and is stored as a readable (not "sensitive") Vercel variable that preview/development
  builds also get (Vercel flags it `readable-secret`). Changing it needs a re-encrypt step or a calendar reconnect.
- **`VERCEL_TOKEN`** (deploy dots) cannot be read-only (CLAUDE.md), so the luc-todo function holds a token that can
  change any project in team teamevo, including holmlodge-shop.
- **Icon proxy** (`api/pprojects.js:59-160`): https only, blocks IP literals and localhost, 4 s timeouts, magic-byte
  check, never SVG, served with `nosniff` + sandbox CSP — good. Gaps: follows redirects to any host, does not check
  what a hostname resolves to, and reads the whole page before cutting it to 200 KB. Low risk (only the token holder
  can trigger it).
- An active shareable bypass link exists on the `luc-todo.vercel.app` alias (created by an earlier session, expires
  ~2 Nov 00:42 UTC). Harmless if production is not protected; let it expire.

### 4.4 Vault (`api/_vault.js`, reviewed in full)
- `node tests/vault_node.js`: **all passed** (1 log line, nothing sensitive). Full mock suite: **172 checks pass**.
- Design is sound: scrypt (N=2^15) + HKDF with `VAULT_PEPPER`, AES-256-GCM with random IV and AAD bound to project and
  entry, POST only, errors log only a code (`:129`), pass expires after 5 minutes.
- Gaps: (1) lockout can be bypassed via the direct Supabase path above; (2) parallel unlock requests all read
  `locked` before any attempt is recorded (`:84-88`), so a burst can exceed 5 tries; (3) a pass stays valid on the
  server for up to 5 minutes after the page "locks" (the server cannot revoke it) — document it.

### 4.5 Leftovers from ROADMAP P0
- **4 — "pull-shop" Vercel token:** cannot be checked from here (no token-listing tool). Luc: vercel.com → Account
  Settings → Tokens.
- **5a — rotate token:** still needed (4.1).
- `.env.example` lists 4 of the 7 variables in use; `README.md` still says `setup01…13`.

## 6. 10-minute device checklist (what mocks cannot tell)

**iPad 2 (5 min)**
1. Close Safari fully, open the app, start a stopwatch: seconds until Today's tasks appear. Do it twice (second =
   cached).
2. Open the Work board, scroll a lane halfway, wait 30 s without touching: does it flicker or jump? (expected yes today)
3. My projects → open a project → tap into "Add an idea", type slowly for 30 s: does the cursor jump?
4. Scroll the Personal list fast: smooth or stuttery? Any blank areas?
5. Tap a few small chips (Resume, filters, "Move to"): how often do you miss?
6. Leave it on the screensaver 2 minutes, tap to wake: seconds until the list is fresh?

**iPhone 13 (5 min)**
7. Same stopwatch test on mobile data.
8. Bottom bar: is "My projects" readable; is anything overlapping "Settings" (bottom-right corner)?
9. Run the "add to-do" Shortcut once; confirm the task appears within 15 s on the iPad.
10. Rotate the iPad to portrait and back on My projects: do lanes keep their scroll position?

**Timing readout (Step 2 suggestion):** yes, worth it (S). A hidden `?perf=1` overlay that shows "boot → tasks"
milliseconds and the last background tick's time would turn steps 1, 6 and 7 into real numbers we can compare before
and after each deploy, which the mocks cannot give.
