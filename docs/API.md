## api/_vault.js
```
// Vault handler, reached as POST /api/pprojects?vault=1 (api/pprojects.js hands the request over). The file name starts
// with "_" so Vercel does not count it as a function (the Hobby plan allows 12 per deployment).
// The per-project vault for sensitive values (environment variables, codes). POST only, so nothing
// sensitive ever travels in a URL (URLs can end up in logs). Body: { action, pass?, ... }. Auth: x-todo-token.
//   {action:'state', project_id, pass?}  -> { configured, set, locked, count, [entries:[{id,name}], pass] }
//        locked = no valid pass: only the number of entries comes back. With a valid pass: names (never values).
//   {action:'setup', password}           -> { pass }   first time only; password 10+ characters
//   {action:'unlock', password}          -> { pass }   403 wrong password; 429 {until} after 5 wrong tries (5 min)
//   {action:'get', id, pass}             -> { value, pass }   one value
//   {action:'save', id?, project_id, name, value, pass} -> { entry:{id,name}, pass }   add or replace
//   {action:'delete', id, pass}          -> { ok, pass }
//   {action:'reset', confirm:'DELETE ALL'} -> { ok, deleted }   forgotten password: wipes every entry and the password
// pass = a short-lived unlock pass (5 minutes, renewed by every call), sealed with a key only the server knows; the page
// keeps it in memory only and drops it after 5 idle minutes or when you leave the page. 401 {locked:true} = expired.
// Crypto: key = HKDF-SHA256(scrypt(password, salt, N=2^15, r=8, p=1), VAULT_PEPPER); entries are AES-256-GCM with a
// random 12-byte IV, bound (AAD) to their project and entry id. Needs env VAULT_PEPPER (32+ characters) and
// db/setup20.sql. Values, names, passwords and passes are never logged and never written to the activity log.
```

//                               (reason: plain text, max 300; acct_*: which account/team/org, plain text, max 80, never passwords)

//   POST {name, status?, meta?}      -> create                         -> { project }
//   PATCH ?id {name?, status?, meta?} -> update; meta replaces the details (empty fields are dropped) -> { project }
//                               a changed reason is logged as its own activity entry
//   PATCH ?order=1 {ids:[...]}  -> reorder (drag and drop): these projects swap among the places they already hold,
//                               in the order given -> { pos: {<id>: n} }. New projects go to the top.

//   POST ?icon=<id> {data (base64 PNG/JPEG, max 200 KB), mime} -> upload a custom icon (resized in the browser)
//   POST ?icon=<id> {from:'site'} -> fetch the first website's icon now and store a copy (422 if the site can't be read)

## api/todos.js
```
// /api/todos — thin, token-gated API in front of Supabase.
// The iPad (iOS 9) and phone only ever talk to this endpoint, never to Supabase directly.
// GET    /api/todos                 -> { today, now, v, todos: [...] }
// GET    /api/todos?v=<fingerprint> -> the same, unless the list is unchanged since the one with fingerprint v: then only
//                                      { same:true, today, now } (about 70 bytes instead of the full list, about 80 KB). v is a short hash
//                                      of the list (not of `now`) and comes back in every full reply. No ?v= (an older cached app, the
//                                      Shortcuts, the ?open=latest check) always gets the full list.
// POST   /api/todos                 -> body { text } (quick add, with shorthand) or { title, due_date, category, pproject_id?, pp_backlog? }
// POST   /api/todos?bulk=1          -> CSV import (desktop). body { rows: [ {row?, title, list, category, due_date, remind_time, repeat, priority, quick, must_today, notes, subtasks} ... up to 100 ], dry? }
//                                      A row with an `id` (an existing task) UPDATES that task using only the columns present; updates are not undone by Undo. Rows may also use words (tomorrow, Mon, 9 Nov, 9am, high, every week); write \| for a pipe inside a sub-task. dry:true only checks the rows. Reply { ok, dry, count, errors:[{row, messages:[...]}], added, cal }. Rules: api/_bulk.js, docs/import/.
//                                      A real run first checks every row and adds nothing if any row is wrong (400 with the same errors).
//                                      Every reply also carries preview:[{row, errors, value:{title,list,category,due_date,remind_time,recur,prio,quick,must,notes,subtasks:[{t,d}]}}] (the rows as the app understood them).
//                                      A real run may send batch:<uuid> (same id for every chunk of one file) and name:<file name>; the ids it added are logged under that batch so it can be undone.
// GET    /api/todos?imports=1       -> { imports: [{id, name, n, created_at, alive, undone_at, undone_n}] } latest 30 CSV imports, newest first (alive = how many of its tasks still exist)
// GET    /api/todos?import_csv=<uuid> -> { name, csv } the clean CSV saved with that import (404 if none); an import sends it as csv:<text> with its first chunk
// POST   /api/todos?import_undo=<uuid> -> deletes the tasks that import added (once). { ok, removed, added, cal }; 404 unknown import, 409 already undone
// POST   /api/todos?scan=1[&list=work|personal] -> photo (v1066: list forces that list on every task and no project is guessed; omit it and Gemini decides work/personal)  photo of handwritten notes -> tasks to review (v1065). Body: the photo itself (Shortcuts "File" body; JPEG, max 3.5 MB), or base64 text, or { image:"<base64>" }.
//                                      Checks the token, asks Gemini (key in env GEMINI_API_KEY, model GEMINI_MODEL, see api/_scan.js) to turn it into import CSV, and keeps the newest scan for review.
//                                      Reply { ok, rows, done, id } (rows 0 and done 0 = nothing readable; done = crossed-out/ticked/highlighted lines kept for the review to match against open tasks, v1069). Errors: 400 not a photo, 413 too big, 429 Gemini busy, 502 Gemini failed, 503 key not set. Nothing is added to the list by this call.
// GET    /api/todos?scan=1          -> { scan: { id, csv, n, created_at, done:{list,titles:[...]} } | null } the newest scan still waiting for review (the app asks once when it opens, and for ?open=scan)
// POST   /api/todos?scan_done=<uuid> -> marks that scan reviewed (added or dismissed). { ok }
// PATCH  /api/todos?id=<uuid>       -> body { done?, title?, due_date?, category?, recur?, recur_until?, low?, remind_time?, list?, focus?, reviewed?, is_session?, items?, notes?, prio?, quick?, must?, blocked?, unblock_action?, pproject_id?, pp_backlog? }
// pproject_id links a Personal task to a Personal Project (see /api/pprojects); null unlinks. Ignored for Work tasks.
// pp_backlog: true keeps a project task on its project page only (Backlog), out of the Personal list.
// DELETE /api/todos?id=<uuid>
// Auth: header "x-todo-token: <token>" (or ?t=<token> as a fallback).
//
// Voice assistant (Jarvis, server only, db/setup25.sql; code in api/_jarvis.js). None of this touches the plain GET, ?v= or the fingerprint.
// GET    /api/todos?jarvis=1[&list=personal|work][&due=today|overdue|week|none][&project=<name>][&limit=25][&include=done,backlog]
//                                   -> { today, now, total, shown, tasks:[...] }: a trimmed list for a small model, in the app's own order (Order, below). Each task:
//                                      { id, title, list, category, due_date, remind_time "HH:MM", prio 0-3, quick, must, blocked, paused, focus, low, recur,
//                                        notes (first 80 characters), notes_len (full length), items {n, done}, overdue, done }. category is the project on the Work list. Empty values are null/false, never left out.
//                                      Finished tasks (the database only returns the last 7 days of them) and Personal Project backlog tasks (pp_backlog) are left out unless include=done / include=backlog.
//                                      due: today = due today; overdue = due before today, and not paused or blocked (Work only); week = due from today to 6 days ahead; none = no due date.
//                                      project = the exact project/category name, any capitalisation. limit 1-100. 400 for a bad list, due, or id.
// GET    /api/todos?jarvis=1&q=<words>[&list][&due][&project][&include][&limit=5]
//                                   -> { today, now, q, total, shown, tasks:[... each with score 0-1] } the best matches, best first (limit 1-20). Same filters as above. Words are matched to the title
//                                      (counts fully), the project/category (0.6) and the notes (0.4); a word matches when it is the same, one letter out (5+ letters) or the start of the other. Score under 0.5 is dropped.
//                                      Spoken filler (the, my, task, please...) is ignored; 400 if no usable word is left. Ties go to the closer title, then open before finished, then newest.
// GET    /api/todos?jarvis=1&id=<uuid> -> { today, now, task } one task in full: everything above plus the whole notes text, items (the sub-tasks, [{t, d}]) with items_summary {n, done},
//                                      recur_until, series_id, successor_id (the next copy of a repeating task), is_session, unblock_action, blocked_at, paused_on, paused_at, done_at, pproject_id, pp_backlog, plan_date, plan_order, created_at. 404 if unknown (or finished more than 7 days ago).
// GET    /api/todos?activity=1[&source=jarvis][&id=<uuid>][&limit=20]
//                                   -> { activity:[{id, at, source, action add|update|delete, todo_id, title, before, after}] } newest first (limit 1-100; id = one task's history). before/after hold only the fields that changed
//                                      (for add: after is the new task, before null; for delete: before is the task, after null). Kept 90 days. { activity:[], unavailable:true } if db/setup25.sql has not been run.
// Write log: a POST (add), PATCH or DELETE on /api/todos that carries the header  x-source: <word>  (letters, digits, - and _, up to 20 characters; anything else is ignored and not logged) is recorded in todo_activity.
//   The reply then also has logged:true|false. A failed log never fails the change. Calls without the header are not logged and cost nothing extra. POST ?bulk, ?scan, plan and import-undo are not logged.
//   PATCH and DELETE first read the task's current values (the same todo_list call), so a tagged call costs one extra database read. A task finished over 7 days ago is not in that list:
//   a PATCH of it is logged with before/after null, a DELETE of it is not logged (logged:false).
// Order (jarvis=1): the app's order, section by section: today's focus (starred), overdue, due today, later (by date), no date (newest first), blocked, waiting on someone, non-urgent, done.
//   Work, inside a section: time of day, must-do-today, priority (!!! first), project priority (On hold last), quick wins, due date, created; each project's hand-made board order and today's Daily Preview order are kept.
//   Personal: no priority; time of day, then created (overdue and later sections go by due date first). When both lists are returned, Personal comes before Work inside a section.
//   Not copied: tasks of on-hold Personal Projects (the app greys them out of counts) are listed like any other.
// What "reprioritise" can change:
//   Work: prio 0-3 (the biggest lever), quick, must (only counts when the task is due today or earlier; clearing the date or moving it later clears it), blocked, due_date/remind_time, project (category),
//         focus, and the position in today's order (POST {plan:[ids], list, date}) or a project's board order (PATCH /api/projects?id {order:[ids]}). Paused is set with POST /api/pause, not PATCH.
//   Personal: prio, quick and must are stored but the app ignores them (no chips, not used for order); blocked and paused are Work-only (the database clears blocked on a Personal task). What does order a Personal list:
//         focus (PATCH focus:true; today only, at most 3 per list - a 4th gives 409 "focus full"; the star lasts until midnight, puts the task at the top, counts as due now and takes an overdue task out of Overdue; setting it clears low),
//         due_date and remind_time (sections by date; within a day, timed tasks first by clock time), low (low:true on a task with NO due date parks it as "non-urgent": last, out of the counts, parked reminders and Insights;
//         giving it a due date or focus clears low; with a due date low does nothing), today's plan order (POST {plan}), and category (a label only).
```
